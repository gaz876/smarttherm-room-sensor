# MQTT transport preparation (experimental, offline)

Public reference: Evgen2/SmartTherm tree ac0af49b918fd7ddd47b15815f2220710e2ba1b0, src/SD_MQTT.cpp blob 8a772a2b34879525b09c6e096ccdf8b691bfaeed; author library Evgen2/arduino-home-assistant tree 44bc145e5cd69767d51b8e83ad8b8efb15a5ce76, HANumber.cpp, HABaseDeviceType.cpp, HASerializer.cpp, HAMqtt.cpp and HADictionary.cpp. The public source uses the MQTT topic setting for the device unique ID and object ID prefix. Derived default command topic format: aha/<id>/<id>_Tindoor/cmd_t or aha/<id>/<id>_Toutdoor/cmd_t, plain decimal payload; indoor/outdoor source indices 3/4. This is a source-derived expectation, not qualification of a particular installed controller or dependency version.

The sensor's existing single-owner measurement snapshot is authoritative. Serialize only fresh valid readings; three decimal digits, locale-independent decimal point, no retained command or invalid substitute. Preserve humidity separately; only temperature has a SmartTherm compatibility flag. Values outside the controller's documented UI range are not eligible for the controller path. Transport must revalidate immediately before publication, avoid persistent/replay queues for temperature, and obtain a synchronized snapshot if called from another task. A stale-sample stop on the sensor cannot prove that the receiving controller rejects stale temperatures; receiver-side fail-safe remains mandatory.

This module has no MQTT broker/client, network connection, hardware, credentials, listener, or startup integration. Topic formatting is an offline helper, no command is sent. Actual MQTT protocol negotiation, authentication/ACL, message routing, session expiry, reconnect, memory bounds and controller compatibility remain gates. Do not use with heating equipment.
